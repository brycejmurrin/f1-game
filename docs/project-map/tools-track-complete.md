## Execution and ownership boundaries

Three different harnesses matter. `verify-track.cjs:111` exports `buildContext(rootOverride, opts)` returning the **Tracks facade itself**, with nonenumerable `_vmContext` and `_vmConsole`. It loads `manifest.TRACK_VM`, expanding `@circuits` through `manifest.CIRCUITS` and `LAZY_SCENERY`; optional `rootOverride` loads that checkout's own manifest. Its GLX stub checks position/normal/index validity and counts mesh vertices. It enables an instanced-batch stub unless `instancing:false`. It does **not** install the baked Assets pack.

`tools/lib/track-build-vm.cjs` (supporting source read, outside the 33-file ledger) returns an **environment** with `Tracks`, `sandbox`, `prims`, `liveBufs`, `mark`, `trim`, `release`, plus selected engine modules. It installs pack assets by default, instruments emitters before `build-props` and `tracks` bind them, and defaults to uncompacted props so `[s,e)` ranges remain valid. `shipped` filters rejected stages and remaps accepted staged geometry via `__blocks`. Callers must consume/remap primitives before `trim(from)` clears primitive retention and live buffers. `release(track)` empties geometry arrays after use while leaving counts and centerline metadata. Clip/coplanar/ground/props-tris use this harness. `float-audit` has its own third implementation: pack assets and primitive bounds, but no shipped-stage reconciliation or `trim/release` API.

The track engine owns centerline sampling, road/terrain meshes, scenery guards, hidden-face stripping and graph replay. These tools consume it; data fixes belong in a circuit's authored definition/scenery, generic emission fixes in `js/track/`, and audit policy changes here or in the corresponding baseline/test. `barrier-jumps` is a pure test-side helper, not evidence that a runtime barrier table was feathered. Gallery helpers own evidence presentation; their output does not assert geometry correctness. External-source tools own conversion/provenance and emit candidate data for author review.

Attached `apex-lsp` was used for named engine navigation: `Tracks.build` → `js/track/tracks.js:471`; `Tracks.buildCenterline` → `tracks.js:47` (delegates to fresh build/cache); `TrackSpace.racingNodeToSource` → `js/track/core/space.js:31` (rounds wrapped start fraction times node count; reverse subtracts racing index); `TrackLine.lineCurvature` → `js/track/core/line.js:371`. The last lookup explicitly reported a module-file fallback with export/caller coverage unverified; its expression was returned and read. CLI consumers outside `js/` were located from source text/imports rather than guessed LSP call graphs. These are navigation results, not a local execution check.
