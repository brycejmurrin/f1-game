## The autopilot red was the box, and it was measured before it was believed

`autopilot.spec.js › ... at suzuka` was red on pages runs 1898, 1899 and 1901
with `page.waitForFunction: Timeout 45000ms exceeded` and an attached state
dump reading `speed: 0, prog: -102` — a car sitting motionless on its grid
slot. That is a physics-regression shape, and round 3 had just changed the
speed cap, the `stoppedOnTrack` pedal gate and the OT proximity rule, so it was
NOT written off as a flake. It was reproduced here first.

It reproduced (suzuka failed, monza passed in the same run), and the
reproduction is what disproved the regression:

- the timeout is inside `load()`, at the `info().track != null` wait, which is
  BEFORE `go()` is ever called — so `speed: 0` is the car correctly parked on
  the grid, not a car that refused to drive;
- the retained Log ring shows the field STILL BUILDING at 65.7 s
  (`[car] build mercedes`, `ferrari`, `redbull` ...). The build never stalled.
  The 45 s wall simply expired first;
- suzuka is the heaviest scenery build in the suite and monza, same file, same
  run, same physics, passed.

`fixtures.js` had already written down the fix at its `TRACK_MS` export: the
hand-rolled track waits "should move to `awaitTrackBuild` whenever one of them
next goes red on a slow box". `awaitTrackBuild` waits on PROGRESS (the Log ring
growing) and reports a genuinely wedged build FASTER than the deadline did, so
this narrows the failure mode rather than widening it.

That was half the answer, and the half that was cheap to believe. Raising the
budget to 180 s made suzuka fail again at 209.8 s — a different failure, with
`phys: null` and the boot track still built, meaning the page never staged
suzuka at all inside the budget. Run ALONE on one worker it passed, at 185.0 s.
So the test was not broken and not slow-booting: it was simply enormous, and a
second worker was enough to push it over any cap.

The cost was never the physics. `runLap` drives 9,000 ticks inside ONE in-page
`evaluate`, and for every one of those ticks the rAF loop beside it was
rasterising suzuka on SwiftShader, competing for the same cores. The test never
looks at a pixel: `probe()`, `physState()` and `maxWallOvershoot()` are all
computed from `G.cars` and `Tracks.wallAt`, never from a frame, and nothing here
calls `render({what:...})` (the one hook that goes stale under headless). So
`load()` now calls `headless(true)` after `go()`, and `game.js`'s `render()`
returns early for the rest of the lap.

|---|---|---|

Three lessons, in the order they were learned. A timeout on a busy box measures
the machine, not the code. The state dump attached to a timeout describes where
the test STOPPED, which is not necessarily where the bug is — read which wait
expired before reading the numbers it printed. And when a test is too slow,
check what it is paying for before deciding what to pay: the budget was the
obvious lever and the wrong one, and deleting the work beat affording it.

## Round 4 — the shadow frame-order bug, one level up

Round 1 fixed WGX's shadow passes writing the CAMERA's instance pack: they now
have their own `batch.shadowInstBuf`, and a canary pins the separation. The same
bug survived one level up, and the canary could not see it because both halves
looked correct in isolation.

`shadowInstBuf` is per BATCH, not per LIGHT. The sun, car and lamp shadow passes
all reach it through ONE caller — `game.js _castPropBatchesShadow`, whose own
comment says it is "shared by the snap-cached sun pass and the per-frame lamp
pass" — which culls the props to whichever light is active and uploads the
survivors. Meanwhile all three passes recorded into ONE deferred command
encoder: `shadowEnd`, `carShadowEnd` and `lampShadowEnd` each stashed it as
`_pendingShadowEnc` to "ride the frame submit", and `_shadowEncoderBegin`
handed the same encoder back to the next pass.

`queue.writeBuffer` is ordered against SUBMITS, so with one submit at frame end
every pass's upload landed before any pass executed. Each pass read whatever the
LAST one packed: the sun's shadow map was rasterised from the lamp's culled set,
and a sun draw of n instances read a buffer holding the lamp's m.

The fix is one line of ordering: `_shadowEncoderBegin` now submits ANY pending
encoder instead of only one whose model ring is nearly full. That threshold was
a memory concern and said nothing about which light had packed the instance
buffer. Cost is up to three submits a frame instead of one. The alternative,
a shadow instance buffer per light, costs memory per batch per light.

The model ring is untouched: slots keep counting across Begins and reset only at
the frame submit, so a submitted pass's slots are never rewritten.

Evidence: `wgx-validate` (real Dawn WGSL + pipeline validation) ok, gpuErrors 0,
wgslParseErrors 0; `webgpu-lifecycle` 81/0; `gfx-probe --backend webgpu` ok with
gpuErrors 0 and a non-blank soft present (meanLuma 44.6). Pixel truth for a
shadow map needs Metal — this is software-verified only until a census run.

The canary now pins the ordering directly, and it bites: restoring the
ring-gated form turns it red (108/1).

## Follow-up review of the mirror-sweep fix (second session, same day)

A parallel session reached the opposite conclusion about `sweepGeoMirrors` —
that the lever could not be made to work and should be removed — and started
removing it. That removal was **backed out**; `94b9a2da`'s fix is what stands.
The disagreement turned on one claim that a check of this repo's own code
settles, and the correction is worth keeping:

- **Claimed:** three cannot survive a released CPU mirror because a lost
  context is restored by re-uploading from `attribute.array` (a three.js
  maintainer says exactly this on the forum, asked the same question about the
  same iOS-memory problem).
- **Actual, in this repo:** Apex 26 never uses three's in-place restore.
  `js/render/three/tlx.js:474-533` (mirroring `js/render/glx.js:407-460`)
  latches the downgrade on `webglcontextlost` and calls `location.reload()` on
  `webglcontextrestored`, bounded to two attempts per tab. A reload re-runs
  `Tracks.build` and rebuilds every geometry from source. What the arrays held
  before the loss is irrelevant to recovery.

Upstream advice about a framework is not automatically true of an application
that does not use the path the advice is about. Withdrawn in
`docs/PERF-FINDINGS.md` §2s.

The review also found that **the sweep is not running at all.** Three gates
stack, one from each session plus the pre-existing env gate:

1. the call site is opt-in behind `apex26.tlxMirrorSweep` (added by the revert
   `a63cab7f`, after the handset report);
2. `sweepGeoMirrors()` declines on mobile (`94b9a2da`, this batch);
3. the env gate above it, which on a phone can never open — `game.js`
   tier-gates the probe at `PerfGov.tier() < 1`.

Measured on the merged tree with `gfx-probe --backend three --lite` at tier 4
(`--ls 'apex26.gfxPreset="low"'`), mobile and desktop arms: `sweeps 0, geos 0,
freedMB 0, gate "--T-"` in both. So `94b9a2da`'s "the desktop win
(PERF-FINDINGS 2r, 31.6 MB of the gap) is untouched" is true of its own change
and not of the tree — nobody is getting that 31.6 MB. Left off deliberately;
re-enabling is a deliberate deletion of gate 1 plus a re-measure, not a
cleanup. `js/render/three/tlx.js` now states all three gates at the call site
so the next reader does not have to re-derive this.
