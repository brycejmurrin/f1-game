## Goal

1. Long-press / right-click the installed icon and jump straight to Race, Time Trial or Daily Time Trial, the Data Hub schedule (Next GP) or the Garage.
2. From the Data Hub schedule tab: "Add race weekend to calendar" (one GP) and "Add whole season" as an `.ics` file, with session times in UTC, reminders at a chosen offset, and a stable UID per session so a re-import updates rather than duplicates. A "NEXT GP" tile with a live countdown on the schedule tab.
3. Decide with evidence which of share target / file handlers / launch handler is worth building.

## Non-goals

- **No Web Push, no notifications API scheduling.** Push needs a push service plus a server holding subscriptions and a sender; this is a static-hosted, backend-free app. The `.ics` VALARM is the no-server substitute (the calendar app does the reminding).
- No live-updating calendar feed hosted by us beyond a CI-generated static file (Design B). No account, no email.
- No change to `js/game.js` size (see Slices), no new network origin, no change to `F1API` rate limiting or TTLs.
- No claim that session times are official: they are what Jolpica returns (see Risks).

## Design

### A. Manifest (Slice 1)
Add `id` (stable app identity, so later manifest edits do not fork the install), `lang`, `shortcuts` (Chromium shows at most ~4 on Android, 10 on desktop; keep 4), and `screenshots`. Shortcut URLs stay inside `scope` and use a query param, not a fragment, because shortcut navigations open a fresh `start_url`-style load and the SW serves `index.html` for any navigation (network-first, `sw.js` fetch handler) so the query reaches the page:

| Shortcut | url | In-app target |
|---|---|---|
| Quick Race | `./?go=race` | the `mb-race` flow (title-flow.js L8) |
| Daily Time Trial | `./?go=daily` | `openTimeTrial(true)` |
| Next GP | `./?go=nextgp` | `DataHub.open("schedule")` via `ensureDataHub` |
| Garage | `./?go=garage` | `openGarage("menu")` |

Each shortcut gets a 96x96 PNG (plus a maskable-safe variant), proposed icons/shortcut-*.png. Install metadata: `screenshots` needs real PNGs (one `form_factor: "wide"`, one `"narrow"`, 2-3 each) -> proposed icons/shot-*.png. Screenshots are pixel sign-off artifacts, so capture with the existing `node tools/shot/agent.mjs <track> <cmd>` surface by a human-supervised run, never as test assertions; keep each under ~300 kB (repo-size note `docs/notes/REPO-SIZE-2026-10.md` is why). `description`/`categories` already exist; add `"sports"` only if the owner wants it (Q3).

### B. Deep-link consumer (Slice 1)
A new tiny module `js/<new>/ui/deep-link.js` (IIFE `DeepLink`, entry in `tools/manifest.cjs`, then `node tools/gen/gen-shell.mjs`; never hand-edit `index.html` blocks): `DeepLink.create(G, deps)` reads `location.search` once at boot, validates `go` against an allow-list of four strings (anything else is ignored, never evaluated), strips the param with `history.replaceState` (same as ghost-share), defers while `UiLayers.inRace()`, and calls the existing entry points. Because `js/game.js` must not grow, the wiring is ONE line in the existing `TitleFlow.create(...)` dependency block at `js/game.js` L8275 only if unavoidable; preferred: `DeepLink` is created from `js/ui/title-flow.js` (already owns boot-time URL consumers L60-61), which has `G`, `openTimeTrial`, `restoreFreePlaySelection`. title-flow.js is not a ratcheted giant (check `tests/data/ratchets.json` before the PR; if it is listed, put the new code in deep-link.js and add one call). Respect first-run gates: if the title intro/onboarding is showing, run after it (`G.state`), so a shortcut never skips consent/onboarding.

### C. Next GP tile and countdown (Slice 2)
Pure helpers in `js/data/schedule.js` (it already owns `raceInstant`/`isUpcoming`; keep it pure and VM-testable): `nextRace(items, now)`, `weekendSessions(race)` -> ordered `[{key,label,startMs,endMs,est:true}]`, `countdown(ms)`. The tile is built in `loadSchedule` with `el()`/`textContent` only. The countdown ticks with ONE `setInterval(1000)` owned by the tab node and cleared when the hub closes or the tab node is hidden (the leak class in `docs/notes/TRACK-SWITCH-LEAKS-2026-10-02.md`); `prefers-reduced-motion` and `aria-live="off"` on the ticking text with a static `aria-label` updated once a minute. API extension: `F1API.schedule()` additionally returns `sessions` per race (extra fields; existing callers ignore them). The cache entry grows ~6x per race (23 races x ~5 sessions, well under the 256 kB cap at L7); check `tests/helpers/f1-api-mock.js` serves the session objects.

### D. The .ics (Slice 3), client-side
`js/<new>/data/ics.js` (pure, LAZY_DATA, no DOM): `Ics.build(races, {alarmMin, includeFp, sprintOnly, now})` -> string. RFC 5545 rules to implement and unit-pin (https://datatracker.ietf.org/doc/html/rfc5545):
- `BEGIN:VCALENDAR`, `VERSION:2.0`, `PRODID:-//Apex 26//Race Weekend//EN`, `CALSCALE:GREGORIAN`, `METHOD:PUBLISH`; CRLF line endings; lines folded at 75 octets (not characters: do not split a UTF-8 sequence), continuation line starts with one space.
- TEXT escaping: backslash, semicolon, comma, newline -> `\\ \; \, \n`. Names like "Emilia Romagna, Imola" and "Grand Prix de Monaco" must survive.
- Times: always UTC `DTSTART:20260307T050000Z`. No `TZID`, so no VTIMEZONE block and no DST arithmetic; the viewer's calendar converts. This is the main timezone-pitfall avoidance (see Risks).
- `UID:<year>-r<round>-<fp1|fp2|fp3|q|sq|s|r>@apex26` : stable per session, never derived from title or time, so a corrected time re-imports as an update. `DTSTAMP` = build time; `SEQUENCE` = stable integer (days since 2026-01-01) so clients prefer the newer copy; `LAST-MODIFIED` optional.
- Durations are estimates and labelled so: practice 60 min, sprint qualifying 45, qualifying 60, sprint 30, race 120 (matches `RACE_MS`, `js/data/schedule.js` L39). Description says "Times from Jolpica schedule data; unofficial, verify with F1.com". `TRANSP:TRANSPARENT` so it does not block busy time.
- `BEGIN:VALARM` `ACTION:DISPLAY` `TRIGGER:-PT30M` `DESCRIPTION:...` ; offset from a picker (none, 15 min, 30 min, 1 h, 1 day). Some clients (notably Apple Calendar on import, Google ignores imported VALARMs on some paths) treat alarms inconsistently: treat as best-effort and say so in the UI (Q2: verify on devices; I could not).
- Delivery: `Blob` + `URL.createObjectURL` + `<a download>`; on iOS Safari the download of `text/calendar` opens the "Add to Calendar" sheet, elsewhere it saves a file. Revoke the object URL after use. Reuse the one hidden-anchor idiom already in the repo (`js/ui/settings-export.js`, around L616) rather than a second one.

**Subscribe vs one-time import.** A calendar *subscription* is an HTTPS URL a client polls (webcal:// or https .ics) and refreshes on ITS schedule (Google: roughly 8-24 h and not controllable; Apple: user-set). A static site has no endpoint that is generated per request, so:
- **Design A, client-side one-time import (recommended v1):** zero infra, works offline from the cached schedule, reminder offset chosen per user, includes only what the user picked. Cost: a later session-time change is not pushed; mitigated by stable UIDs + SEQUENCE so re-importing updates events (client-dependent: Google and Outlook update by UID, Apple usually does).
- **Design B, CI-generated static feed (proposed v2):** a scheduled step (the repo already has nightly crons, ci.yml L216, and pages.yml L22) runs a a proposed calendar-generator script under `tools/ci/` (named gen-calendar) that fetches Jolpica ONCE per run (1 request, far below limits), writes a static season .ics (default 30 min reminder, all sessions) into the staged site, and pages.yml publishes it. Users subscribe to `https://brycejmurrin.github.io/f1-game/<file>.ics`. Pros: auto-updates when times change, one fetch per CI run not per user, subscribe works from any device. Cons: freshness = deploy cadence (the train poke makes that minutes, but a pure time-change would need a deploy; a scheduled pages.yml run exists but only publishes when the tip changed, see pages-reuse-verdict.sh), the file is part of the deploy so it must pass `tools/desktop/stage-files.mjs`, fixed reminder, and a licence consequence (Q1).
- **Recommendation:** ship A first (Slices 2-3), prove the builder with unit tests, then B reuses the SAME `js/<new>/data/ics.js` via a Node `vm` load (the pattern `tests/unit/data-schedule-tz.test.mjs` uses) so there is one serializer.

## Jolpica / OpenF1: limits, terms, credit, caching, offline

- **Jolpica limits** (verified 2026-10-04 at https://github.com/jolpica/jolpica-f1/blob/main/docs/rate_limits.md): unauthenticated 4 requests/s burst, 500/hour sustained, "subject to change, and will decrease"; they ask for caching and efficient filters. This plan adds ZERO requests: Slices 1-3 reuse the one 24 h-cached schedule call; Design B adds one per CI run (a handful/day). Sustained limit is per IP, so shared NATs matter: never poll from the countdown (it reads the cached list only).
- **Jolpica terms** (https://github.com/jolpica/jolpica-f1/blob/main/TERMS.md, last updated 2025-08-27): free for NON-COMMERCIAL use; data licensed CC BY-NC-SA 4.0; contact admin@jolpi.ca for commercial use; no uptime or accuracy guarantee; may block abusers; terms can change. Consequences: (a) attribution in the UI and inside the .ics (`X-WR-CALNAME`/DESCRIPTION line "Schedule data: Jolpica F1 (CC BY-NC-SA 4.0)"), (b) a published static .ics is a redistributed adaptation, so ShareAlike suggests licensing the file CC BY-NC-SA 4.0 too (a plain licence note in the file header and the site; Q1 asks the owner), (c) the game must stay non-commercial.
- **OpenF1** (https://openf1.org/ FAQ, read 2026-10-04): free tier 3 req/s and 30 req/min; non-commercial/educational/fan use; data under CC BY-NC-SA 4.0; live data (in-progress or ended under 30 min) is paid. The schedule path does not need OpenF1; `F1API.meetings` (`js/data/api.js` L152) stays the optional cross-check. Do NOT source session times from OpenF1 for the calendar (30 req/min is shared with WATCH/RACE IT paging).
- **Caching/offline**: schedule lives in localStorage `apex26.api.*` (24 h TTL, evicted first under quota by the sweep, api-transport.js L76-124). Offline, the tile and `.ics` work from that entry if present; if absent the buttons show the existing `emptyMsg` copy and stay disabled (never blank, never a thrown rejection). The SW does not cache the API (cross-origin), and this plan keeps it so. A season that rolled over (`season()` reads the clock, api.js L18) between Jan 1 and the first race shows an empty list: the tile says "No races scheduled yet".
- **Timezones/DST**: emit UTC only; display via the viewer's zone from one instant (house rule, `js/data/schedule.js` L3-10). Tests pin `process.env.TZ` before any `Date` use (see `tests/unit/data-schedule-tz.test.mjs` header). Countdown math is epoch-ms subtraction, never local-calendar arithmetic, so DST transitions inside the countdown window cannot skew it. A date-only entry (no `time`) must NOT become an event at 00:00Z: skip its alarm and emit an all-day `VALUE=DATE` event or omit it.
- **Unverified/estimated nature**: Jolpica times are community-maintained and can change (and Ergast-style feeds have shifted session times after publication); session END times are not in the feed at all (we assume durations); sprint weekends use a different session set. Every surface says "unofficial, check F1.com", and the NEXT tile marks times "est." until the owner decides otherwise.

## Risks

1. **Service worker regressions** (highest blast radius): any `sw.js` touch (share target POST route, optional seeds) can break offline boot for every installed user. Mitigation: Slices 1-3 need no `sw.js` edit; Slice 4's SW work is gated on `test:service-worker` + offline-precache-check.cjs and kept separate.
2. **Wrong or stale session times presented as fact / licence exposure**: users could miss a session; a published `.ics` is a CC BY-NC-SA redistribution. Mitigation: UTC from the feed only, "est." labelling, attribution in file and UI, subscribe feed gated on owner sign-off (Q1).
3. **Deep link bypassing gates / leaking state**: a `?go=` that skips onboarding or fires mid-race. Mitigation: allow-list of four, run after title/onboarding, defer in race, strip the param. Also: shortcuts are Chromium-only, so iOS users see nothing (expected, not a bug), and the countdown timer must be torn down with the hub (interval leak).
4. Calendar client divergence on VALARM and UID-update behaviour (not testable here), plus repo size from screenshots (keep small).
5. A `manifest.json` `id` added later changes the installed app identity on some platforms; set it once, deliberately, to the current resolved start URL (Q6).
