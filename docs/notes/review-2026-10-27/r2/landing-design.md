Read at `origin/claude/f1-game-project-26h3ng` (fetched 2026-10-27) plus open PR #3921 (`origin/cursor/dispatch-page-cutoff-4e2a`, c73f4611).
Live ruleset `Deploy-reset` (read-only `gh api repos/brycejmurrin/f1-game/rulesets/<id>`): required_status_checks =
`[{context: "gate", integration_id: 15368}]` (15368 = GitHub Actions), strict=false, 0 approvals, no code-owner review,
no bypass actors, merge method `merge`. **`CI` is NOT a required check**, despite what docs/WORKERS.md:23 and :103 say.

Sources (read 2026-10-27):
- events-that-trigger-workflows: `pull_request` GITHUB_SHA = "last merge commit of the pull request merge branch" (the PR's own workflow file); fork PRs get no secrets/read-only token, so same-repo PRs DO get secrets. `pull_request_target` "runs in the context of the default branch of the base repository"; "Avoid using this event if you need to build or run code from the pull request." `workflow_run` "is able to access secrets and write tokens", GITHUB_SHA = last commit on default branch. https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows
- GitHub Security Lab, "Preventing pwn requests": split = unprivileged `pull_request` job uploads an artifact, privileged `workflow_run` consumes it; "Artifacts from untrusted PRs are themselves untrusted". https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/
- Troubleshooting required status checks: a check AND a status with the same name, selected as required, are BOTH required. https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks
- Cache poisoning (Actions runtime token from inside a build writes caches other workflows restore): https://adnanthekhan.com/2024/05/06/the-monsters-in-your-build-cache-github-actions-cache-poisoning/ , https://adnanthekhan.com/2024/12/21/cacheract-the-monster-in-your-build-cache/

SEVERITY | file:line | concrete scenario | fix

CRITICAL | .github/workflows/land.yml:54-56, 233-246, 342-386; ruleset `gate`@15368 | `pull_request` runs the PR's OWN land.yml with secrets (same-repo branch). A worker PR that edits land.yml so `post` writes `gate: success` (statuses: write) and `arm` runs `gh pr merge` with `secrets.LAND_TOKEN` merges itself to the deploy branch with no gate. The same works from ANY new workflow file in the PR (a GITHUB_TOKEN status is Actions app 15368, so it satisfies the ruleset), or from a `workflow_dispatch` of an edited non-ci/pages workflow on the branch (the dispatched ref's file runs; github-mcp-guard only asks for pages/ci). | Move resolve/post/arm to `pull_request_target` (same types; runs the deploy branch's file; these jobs check out nothing, so they are pwn-request safe). Put `LAND_TOKEN` (and any gate-signing App key) in an Environment whose deployment branches = deploy branch only, so a `pull_request` run (ref refs/pull/N/merge) cannot read it. Post `gate` with a dedicated GitHub App token and set the ruleset's `integration_id` to THAT app, so no GITHUB_TOKEN status counts. Add a push ruleset file-path restriction on `.github/workflows/**` (bypass: Bryce).
HIGH | docs/WORKERS.md:23, :103; tools/ci/merge-gate.mjs:85-95; land.yml:314-316 | The ruleset does not require `CI`: CI is enforced only by merge-gate's `ci` row and post's re-read, which accept the newest check-run NAMED `CI` from app `github-actions`. A PR adding a workflow with a job named `CI` that exits 0 (or editing ci.yml's `ci-verdict`) gets a higher-id green `CI` check-run → ci row ok. | Add `CI`@15368 to the ruleset (or a ruleset "require workflows" rule pinned to the deploy branch's ci.yml). In ciVerdict/post, require the check-run's check_suite to belong to the workflow run whose `path` is `.github/workflows/ci.yml` and whose event is `pull_request`. Fix the WORKERS.md claim.
HIGH | land.yml:73-75, 83-90 | Workflow-level concurrency is evaluated before job `if:`. ANY pull_request label event on PR N (`needs-owner` from the dispatcher, `priority`, `run-ci`, `claimed`) or an `edited`-free synchronize starts a run in `land-N` with cancel-in-progress → cancels the in-flight `workflow_run` re-gate fired when CI finished; the new run's `resolve` is skipped (label ≠ land/hold). `gate` stays pending "CI running" forever on a green PR. The comment at :71 ("a CI or train re-gate never cancels, it queues") is wrong for the victim side. | Make the group key include the label filter: e.g. `group: ${{ <relevant-event> && format('land-{0}', n) || format('land-noise-{0}', github.run_id) }}` (ci.yml already does this for labels), or set cancel-in-progress only for land/hold/draft/synchronize events.
HIGH | land.yml:196-205 (`setup-node cache: npm`), merge-gate.mjs:169-175, 234-235 | land-gate runs the PR's `gen:check` and ratchet tests on a runner whose run is in the default-branch context (workflow_run) or with the PR's scope; untrustedEnv strips env vars but the code comment admits the same uid can read parent/worker process env and memory. An in-build cacheract-style payload writes a poisoned npm cache entry; ci.yml/pages.yml on the deploy branch restore it → code execution in the release train. | No `cache:` in land-gate (or `actions/cache/restore` only); run PR code in a job with `permissions: {}` and no runtime-token-holding action after it; better, run gen/ratchets under the PR's own `pull_request` CI and only CONSUME a result.
HIGH | land.yml:211-229, 303-321; merge-gate.mjs:229-240 | Verdict-file forgery: a detached process started by the PR's gen:check (same uid; the runner reaps orphans only at job end) rewrites `verdict/<n>.json` after merge-gate exits and before upload-artifact (`if: always()`): `{code:0, head:<real head>, tip:<current tip>}`. post only re-checks head, draft, labels and CI, so the TRUSTED rows (plan, distance, open/hold) plus gen/ratchets are bypassed; arm's tip check passes because the forged tip is the real tip. | Compute plan (PR body via API), distance (compare API or a trusted fetch) and hold/open in `post` itself, never from the artifact; take only gen/ratchets from the untrusted leg, and treat even those as "as trustworthy as the PR's own CI".
HIGH | tools/ci/dispatch.mjs:186-192, 288, 383-384 | `landProblem` reads check-RUNS only; since #3917 `gate` is a commit STATUS. A `land` PR whose `gate` status is failure (Plan open, ratchet, distance, "not asked") and whose check-runs are green is "waiting on CI/gate/train" forever: never `needs-owner`, never re-owned. | Also read `commits/{sha}/status` (combined) and treat `gate` failure, or `gate` pending older than N h, as a problem.
MEDIUM | land.yml:74, 342-386 | Two Land runs in DIFFERENT groups (`land-tip` train re-gate and `land-N` PR run) can both pass arm's tip re-read and arm two PRs onto the same tip within seconds; the second merge is an ungated combination (gen/ratchets/distance measured without the first). | Job-level `concurrency: { group: land-arm, cancel-in-progress: false }` on `arm`; re-read the tip immediately before the merge; long term a merge queue (`merge_group`) gates the exact combination.
MEDIUM | land.yml:274-286; ruleset strict=false | `gate: success` stays on the head after the tip moves. If GitHub reported BLOCKED at arm time (real auto-merge, header :6-9) or anyone merges by hand / a hookless Codex lane arms it, the PR lands later onto a tip it was never gated against. | On every deploy-tip move post `gate: pending` ("tip moved") on all `land` heads before re-gating (cheap, no checkout), or adopt a merge queue.
MEDIUM | land.yml:278 | Compare-and-set by string time: GitHub `created_at` has second precision (`…:05Z`), AT has nanoseconds (`…:05.123Z`); `Z` > `.` so a status posted in the same second BEFORE resolve read reads as newer and this run's verdict is dropped. Also an OLDER run that posts after a newer run's resolve wins (it drops the newer verdict). If that was the last event, `gate` is stuck. | Compare parsed epoch values; drop only when the existing status was posted by a run with a LATER resolve time (embed AT in the status description/target_url and compare those), not by post time.
MEDIUM | land.yml:74 (`|| 'tip'`) | `workflow_run.pull_requests` is empty for forks and can name a PR on another base; such CI re-gates share `land-tip` with train runs. GitHub keeps one pending run per group: a newer pending run cancels the older pending one, so PR X's CI-finished re-gate is dropped when PR Y's arrives. | Key on `workflow_run.head_sha` (or run id) when pull_requests is empty; never share the train's group.
MEDIUM | ruleset + #3917 migration | PR heads that already carry an old `gate` CHECK RUN (Actions app) now also get a `gate` STATUS; per GitHub docs both are required, so a stale red/"Expected" check run blocks a green status. | Re-push (or empty commit) open `land` PRs once; add a merge-gate/post warning when a `gate` check-run exists on the head.
MEDIUM | land.yml:125-130, 377-384 | A red train re-gates nothing; only one PR is armed per run; with `LAND_TOKEN` unset a merge starts no train. Green `land` PRs then sit unarmed until a green train or the 6-hourly cron. | Re-gate on red trains too (gate rows don't depend on train colour), and after an arm with GITHUB_TOKEN schedule a re-gate (e.g. `repository_dispatch` with LAND_TOKEN) instead of waiting for the cron.
MEDIUM | dispatch.mjs:24-27, 262-268, 439-441 | Claim-after-launch race: two accounts' dispatchers (WORKERS says both edit the Board) plan in the same window, both see no launch comment, both create_session for the same issue. RECORD_LAUNCH failing (or, in #3921, run verbatim with `--session <the new session id>`, which recordComment rejects) leaves no claim → relaunch next hour. Worker-side "older claim wins" limits damage on issues, not on CONTINUE PR takeovers. | Post a provisional `dispatch: launching … nonce=<x>` comment, re-read, proceed only if it is the oldest live one; or partition work per account (config `account`, issue/PR parity or an `acct:` label).
MEDIUM | dispatch.mjs:249-257, 261 (+ #3921 childSessionIds) | maxLiveWorkers is per dispatcher: with children-only lookup, the other account's sessions are never fetched; their launch comments count as live for 2 h only. Two accounts can run ~2x the cap, and a long-running worker of either account drops out of the count after 2 h. | Count `claimed`/`lane:*` open work items whose newest launch/claim comment is < cost-cap duration as live regardless of account; or match by session id in launch comments, not titles.
MEDIUM | .claude/hooks/merge_policy.py:38-41, 155-201; github-mcp-guard.sh:83-94 | The deny text says "the gate writes no receipt, so this door stays shut", but the code still ALLOWS a merge/arm when `artifacts/merge-gate/<pr>.json` exists with kind merge + matching gateFiles hashes, which any session can hand-write (gate-receipt.mjs WRITABLE_KINDS = ["ready"]). | Unconditional deny for merge_pull_request / enable_pr_auto_merge (and bash-guard's `gh pr merge`), no receipt path.
LOW | github-mcp-guard.sh:95-115 | No rule for `issue_write`/label edits: a session can remove a `hold` it did not set (labels-replace semantics drop it silently) or add `land` without ready-gate. Merge-gate re-checks Plan/CI, but the "whoever set it removes it" veto is unenforced. | Ask on any label write that removes `hold` or replaces the label set; land.yml could record who set `hold` (timeline API) and refuse a removal by a different actor.
LOW | .claude/hooks/launch-gate.py:33-37, 59-67 | Fails open on its own errors, and a receipt is just `{kind:"launch", ok:true, page:{sha256:<any hex>}, at:<now>}`, writable by hand; launch-gate.mjs's mtime/timestamp checks only bind the tool, not the hook. | Hook re-hashes the saved page named in the receipt and re-checks its timestamp; onFailure block for this hook.
LOW | #3921 dispatch.mjs readState (`issues?state=closed&since=` 48 h) | A child whose PR closed > recentClosedHours ago and was never archived (dispatcher down a weekend) is never looked up again: a leaked session. | Keep the session id list in the Board comment until archived, or widen `since` to the cost-cap lifetime.

## Top 10
1. CRITICAL: PR-controlled workflows (`pull_request` runs the PR's land.yml with LAND_TOKEN; any workflow's GITHUB_TOKEN status is app 15368) can post `gate` and self-merge → pull_request_target + Environment-scoped secret + dedicated-App `gate` + `.github/workflows/**` push restriction.
2. HIGH: ruleset requires only `gate`; `CI` is forgeable by any job named `CI` → require `CI` (or a pinned required workflow) and pin the ci row to ci.yml's run.
3. HIGH: label noise cancels the CI re-gate via workflow-level concurrency → stuck pending `gate`.
4. HIGH: npm cache in the land-gate leg runs PR code in default-branch cache scope → poisoned train.
5. HIGH: forged verdict artifact bypasses the trusted rows (plan, distance) → compute them in `post`.
6. HIGH: dispatcher's landProblem ignores the new `gate` status → red-gated `land` PRs never re-owned.
7. MEDIUM: cross-group arm race lands an ungated combination → global `land-arm` concurrency / merge queue.
8. MEDIUM: stale `gate: success` survives tip moves (strict=false) → mark pending on tip move.
9. MEDIUM: string-time compare-and-set drops newer verdicts (same-second, out-of-order posts).
10. MEDIUM: dispatcher claim-after-launch race across two accounts + RECORD_LAUNCH placeholder → duplicate workers.
