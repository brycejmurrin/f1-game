# M1 — garage livery edits: what each edit leaks or rebuilds (TLX), 2026-10-18

Ask (Bryce, 2026-10-18 ~04:10Z): "when editing my livery in the garage after enough changes and the garage re
rendering it greatly slows down and lags. I am running on three js with web gpu backup." PR #2812, branch
`cursor/garage-livery-leak-m1a7`. Box: cloud container, SwiftShader, no `/dev/dri`, no Vulkan ICD — TLX ran on
three's WebGL2 backend; the WebGPU leg could not run here (see Not measured).

## Method

`scratch/m1probe.mjs` (untracked): headless Chromium at 844x390 (phone landscape) with `?three-devtools=1`,
GARAGE → LIVERY → create, then N edits through the editor's own inputs (`input` + `change`, which flushes the
75 ms preview debounce), 3 frames after each. Per edit: `renderer.info.memory` geometries/textures, three's live
RenderObjects, pipelines and programs, `renderer.backend.createTexture/destroyTexture` calls (render targets
excluded), TLX `coState().runs`, `memState()` materials, canvases created and alive after GC, forced-GC JS heap,
and wall time per edit; a CPU profile of one edit; heap snapshots at edits 10 and 100. Edit kinds: body colour,
accent, finish, number font, sponsors, spine design, fin shape, and a unique wing (c2) colour per edit, as a
dragged colour picker produces.

## Findings

| # | What | Evidence | Status |
|---|---|---|---|
| 1 | **Aero flap meshes accumulate.** `drawAeroFlaps` draws the turntable's wings from `CarMesh.getAeroFlapSet` / `getAeroFlap`, keyed on wing colour + finish, FIFO-capped at 64 sets / 128 elements (sized for a race grid). Every wing-colour or finish edit mints a new 1272-vertex set; the old ones stay until 64 more edits push them out, each with a hidden coalesced TLX run (its RenderObject and CO_CAP x 19-float instance buffer) that the instanced-run pass walks every frame. | 7-kind mix: geometries 40 → 51 and RenderObjects 41 → 47 over 42 edits; the unregistered-geometry dump named the 1272-vertex `iM0..3 + instanceTint` run views, 2 → 13. | FIXED: `CarMesh.releaseIdleFlaps(ms)`; the garage's `spMeshBust` frees flap meshes not drawn for 2 s. The race path never calls it. |
| 2 | **GPU texture churn per edit.** Each edit frees and re-creates the same-sized atlases: the car's decal atlas (and on desktop its deferred 2048x2560 hi-res swap, ~27 MB), the bay's dress and live screens. Every one a fresh GPU allocation and fresh bind groups; on Safari's WebGPU a destroyed texture's memory is held while any bind group that referenced it waits for GC ([WebKit #76225](https://github.com/WebKit/WebKit/pull/76225)). | `backend.createTexture` +3 per edit on the base (spec: 15 → 30 over 8 edits); `info.memory.textures` stays flat because each is destroyed too. | FIXED: TLX retired-texture pool; three r186 `Textures.updateTexture` re-uploads a version bump into the existing GPU texture (creates only while `isDefaultTexture`, no size check), so a same-size, same-kind retired texture is re-filled in place. Capped at 4, aged out after 10 s. |
| 3 | **An editor draft cached under the saved livery's key** (issue #2796 item 4). The race body caches key on the saved livery id; a miss while the draft was live stored draft paint, and CANCEL kept it. | Code-traced; `livery-draft-mesh-cache.test.mjs` fails 2/3 on the base. | FIXED: `invalidateCustomMeshCaches(teamId)`; `endLivPreview` drops the team's four body caches. |
| 4 | Per-edit constant cost: a body-colour edit rebuilds the whole bay (shell, floor, props, equipment) because the room keys its geometry on the paint; plus `Car3D.build` (~130 ms on this box, `smooth` ~60 ms of it) and the atlas repaints. | CPU profile of one c1 edit: main thread ~0.5 s busy, the rest of the ~9 s edit idle waiting on SwiftShader. Constant across N (no growth). | NOT CHANGED: a constant, not a leak; a debounced room rebuild is the lever if it is still felt. |
| 5 | `resolveLivery` is not memoised while a draft is live (`custom-liveries.js`): every call per frame re-runs `pickLivery(migrateLivery(...))`. | Code-traced. | NOT CHANGED: constant per frame, small. |

Refuted (do not re-report): the mirror glass/fallback meshes are keyed on `cockpitMirrorGlass` quads, which are
memoised per scale (no per-build mint); the livery undo history is capped at 50; the crew-mesh cache is FIFO-capped
at 32 and frees; decal materials are released with their texture; program/pipeline counts stay flat (6 pipelines,
4 VS / 6 FS) through 100 edits; canvases alive after GC stay at 5.

The base's geometries and render objects climb one per edit until the 64-set flap FIFO cap (~62 edits), then
stay pinned there; its GPU textures are created and destroyed ~3.5 per edit. Head's residual GPU textures

window; a real GPU edits in a fraction of that. Time per edit is SwiftShader's (the main thread is ~0.5 s busy;
the rest waits on the software GPU), so it does not show the per-frame cost of the hidden runs a real device pays.

Regression: `tests/specs/garage-livery-churn.spec.js` — base `= run failed` (GPU textures 15 → 30 over 8 edits,
geometries 13 → 17), head `= run passed`; node: `car-mesh-crew-cache`, `tlx-texture-release`,
`livery-draft-mesh-cache` each fail on the base.

## Not measured

- **WebGPU backend.** No GPU and no Vulkan ICD in this container, and three's WebGPU path dies under SwiftShader.
  Finding 2 (texture churn) is the WebGPU-relevant one; the pool is backend-agnostic in TLX (three's `Textures`
  sits above both backends). A real-GPU check needs a garage-edit leg on `gpu-census.yml` (P1 holds the token).
- Frame times on this box are SwiftShader's, indicative only.

## Follow-up: the churn spec measured frames, not memory (2026-10-18, after #2829)

`garage-livery-churn.spec.js` went red on the deploy tip 75864637 (push run 39120209779: geometries `8 → … → 8 → 12`).
Not a leak, and not #2829's zone meshes. `renderer.info.memory.geometries` and three's RenderObject count follow what
the last frames drew (tip reads: `11 → 34 → 12 → 34 → 12`), and even TLX's live-geometry census after a forced GC swings
~22 between edits as the bay's rebuild lands (35/57 on the tip, 38/61 on f3b2d89d), flat on both. The spec now bounds
the leaking cache itself, `CarMesh.flapState()` (sets/elements held), plus GPU textures created, both counts that do not
depend on the frame a read lands on. f3b2d89d with only the getter: `= run failed` (flap sets 5 → 6 → 7 → 8 → 9, 1-3 GPU
textures per edit); tip: `= run passed (3/3)`.
