# Perf hunt P2: the per-frame sim loop (physics, AI, race), 2026-11-03

Kind: measurement · Re-measure-by: 2027-02-01

Lane: issue #4533 (orchestrator A's perf hunt, relaunched by orchestrator B). Slice: the per-frame CPU of the
simulation: the `js/game.js` frame loop, `js/physics/**`, `js/race/**`, AI, and the tick cost of `js/input/**`,
`js/net/**` and `js/workers/**`. Target: Bryce's iPhone at 844×390 on THREE PATH: WEBGPU with 22 cars. Physics
behaviour must not change. Prior art read first, not re-reported here: `CPU-HUNT-2026-10-24.md` (which says V8's boxed
doubles cost nothing on JSC), `PERF-ALLOC-HUNT-2026-10-17.md`, `PERF-HUNT-CPU-2026-10-17.md`, `PERF-HUNT-2/4/8`
and the `js/race/car-fields.js` header (one hidden class per car, double fields warmed up front).

## Verdict

**On JavaScriptCore the whole 22-car sim costs 0.52–0.93 ms per frame**, about 3–6 % of a 16.7 ms frame. The hot
functions have been tuned by eight earlier hunts. Every remaining candidate is worth under 0.05 ms/frame on JSC, and
each one would need a rewrite that changes float rounding order, which the determinism rule does not allow.
**This PR changes no game code.** For Bryce's phone the frame budget sits in the renderer and the HUD (the P1/P3
lanes), not here. Two findings change how the sim *should be measured*: §2 and §3.

## Method

Every number below comes from the real `js/game.js` in the Node VM harness (`tools/lib/game-vm.cjs`). The renderer is
stubbed, `__apex.headless(true)` is on, the field is 22 cars, and the player holds throttle with steer 0.02. The run
does 600 warm frames, then measures. The same harness ran on two engines:

- **V8**: Node v22.23.4.
- **JSC**: Bun 1.4.4. Bun runs JavaScriptCore, the engine in iPhone Safari, and its `node:vm` runs `game-vm.cjs`
  unchanged.

The x86 cloud vCPU is not an A-series core. Read the JSC numbers as an order of magnitude, not as device milliseconds.

The scripts were untracked, in `scratch/p2/`. The timing script, in full:

```js
// scratch/p2/time.cjs: node or bun, then: <track>
const { createGame } = require("../../tools/lib/game-vm.cjs");
(async () => {
  const g = await createGame({ track: process.argv[2] || "monza", carMeshes: false });
  const A = g.apex; A.headless(true); A.setInput({ throttle: true, steer: 0.02 });
  g.step(600);
  const w = [];
  for (let i = 0; i < 5; i++) { const t0 = performance.now(); g.step(300); w.push((performance.now() - t0) / 300); }
  console.log(JSON.stringify({ msPerFrame: w })); g.close(); process.exit(0);
})();
```

The other scripts:

- **CPU profiles**: `bun --cpu-prof --cpu-prof-interval=100` over 6000 frames, and the inspector `Profiler` at 100 µs
  under Node. Summaries come from `tools/perf/cpuprofile-summary.mjs`, plus a `positionTicks` line roll-up.
- **Call counts**: `Profiler.startPreciseCoverage({callCount: true})` over 300 frames.
- **Field-type census**: a `Proxy` around every `CarFields.warmDoubles` scratch object, hooked in through a
  `CarFields` accessor in `onSandbox`, plus car-field sampling every third step over 1500 frames.
- **Browser cross-check**: `tools/perf/profile.mjs monza --mode cpu` (Chromium, SwiftShader).

## 2. `node:vm` makes V8 global reads ~100× slower, and game-vm turns every module `const` into one

Microbench, 5×10⁷ loop iterations in a `vm.createContext` context (`scratch/p2/vmglob2.cjs`), times in ms:

| top-level binding read in the loop | V8 vm context | V8 main context | JSC vm context |
|---|---|---|---|
| `var K` (a global property) | **4815** | 43 | 48 |
| `const K` (script-scope lexical) | 42 | — | — |
| a `function g()` declaration, called | **4471** | — | — |
| `const g = () => …`, called | 75 | — | — |

A contextified sandbox resolves global *properties* through an interceptor. Script-scope lexicals resolve without it.
`game-vm.cjs runFile` rewrites `^const` → `var` (`tools/lib/game-vm.cjs:608`; also `track-build-vm.cjs:88` and
`vm-debug-preload.cjs:38`). That turns every module global (`AiDrive`, `Tracks`, `TyreModel`, game.js's
`clamp`/`lerp` aliases …) into a slow property. Top-level `function` declarations in `js/game.js` are global
properties either way.

Experiment: a scratch copy of the harness that runs the sources unrewritten, exposes each top-level `const` to the
harness through a configurable accessor on the sandbox, and keeps the rewrite for `js/ui/screen-looks.js` only (see
below). Monza, V8, three runs per arm on the same box:

| arm | ms/frame | player state after 2100 frames |
|---|---|---|
| shipped harness | 2.27–3.33 | `s` 773.852560547427, `x` −12.169761189573888 |
| lexical consts | 1.85–2.78 | bit-identical |

The two arms' spreads overlap, so the size is not proven. The medians point to about 20 % faster. The rest of the
gap to JSC is the `function` declarations.

Consequences:

- V8 profiles taken in game-vm overweight every cross-module call and every tiny helper. In the node:vm profile,
  `weather-arc hasTM` (`typeof TyreModel`) and `vTop` (`getVMAX`/`getPACE`) were top-5 self-time lines. In
  Chromium they do not appear. **Rank sim work from a JSC (bun) or Chromium profile, never from a node:vm one.**
- `tools/perf/hot-bench.mjs` (the step bench) and every game-vm test pay this cost. The game-vm CI partitions are
  the slowest node shards (`AGENT-PROCESS-RESEARCH-2026-09-16.md`: `vm` 9.4 min).

Proposed follow-up (not this lane; owner is `tools/lib` plus the test helpers): evaluate `js/` unrewritten and give
the harness lexical access through accessors or `vm.runInContext(name)`. That also brings the VM closer to the
browser, where a top-level `const` is not a `window` property either. Blocker found on the way: under the VM's fake
DOM, `js/ui/screen-looks.js`'s eval-time `build()` reaches `PauseOpts.apply` → `typeof ScreenLooks` while
`ScreenLooks` is still uninitialized, and that throws for a lexical binding. Check first whether the browser takes
that path too (if it does, that is a latent bug), then move the call after the assignment.

## 3. Cross-engine float divergence, measured

The same seeded race on V8 and on JSC ends at the same pose on monaco (to the last bit). It differs in the ~12th
significant digit on monza and spa: player `s` 773.852560547427 vs 773.8525605474359 after 2100 frames. Library
transcendentals differ between engines (`ENGINEERING-PRACTICE-NOTES.md` predicted this). It is harmless as built:
`js/net/netplay.js` replicates state, with each peer owning its car (docs/MULTIPLAYER.md). It does mean a recording
or a replay check must never compare an iPhone run with a Chromium run bit for bit. `tests/unit/physics-
characterization-vm` compares V8 with V8.
