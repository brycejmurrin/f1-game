## 1. Mirror cadence: the same on every backend; the "1 in 4" was a counter reset

#4272 item 1 read census 40868057244 as "TLX renders the mirror on 450 of 450 frames, WGX on 110 of 422". The same
fields on the baseline census, read at the end of the window:

| leg | mirror-pass `drawn` | backend `renders` | backend `glass` | window frames |
|---|---|---|---|---|
| TLX WebGPU | 501 | 501 | 500 | 500 |
| TLX WebGL2 | 517 | 517 | 516 | 512 |
| WGX | 349 | **36** | 348 | 348 |
| GLX | 634 | **103** | 633 | 628 |

- `drawn` is `mirror-pass.js`'s own count of passes it issued (`_drawn++` after a pass that drew). It is backend-neutral,
  and it equals the glass draws and the window frames on all four legs. So every backend renders the rear view on
  every frame.
- The backends' `renders` are not the same counter. TLX's `_mirRenders` is a lifetime count. WGX's `_mirrorFree()`
  (wgx.js) and GLX's `mirrorFree()` (glx/post.js) set it back to 0 whenever the target is re-allocated. So WGX's 36 and
  GLX's 103 are the frames since the last re-allocation, not a cadence.
- The cadence comes from one place for all backends: `mirror-pass.js` `QUALITY[].every`. The rungs `full` and `lite`
  draw every frame by design ("a mirror that updates at half rate reads as lag"). `low` draws 1 in 2, `min` 1 in 3.
  The governor stayed at tier 0–1 on every leg (beats `ti`), so every leg sat on `full` or `lite`.

So the open question is not a backend difference: **a mirror scene pass every frame is the design on a phone's `lite`
rung.** Cutting it to 1 in 2 on `lite` is a look change (mirror lag), so it goes to Bryce as a decision, with the
numbers from the census below (§Decisions).

What the 36 and 103 do say is that WGX and GLX re-allocated the mirror target late in the window. On both legs the
re-allocation lines up with a governor move in the beats: WGX's render scale went 0.5 → 0.9 about 2 s before the end,
and GLX's tier went 0 → 1 about 4 s before (a rung change resizes the target after the 90-frame dwell). WGX's mip
count follows the inset's size in present pixels (`_mirLevels` → `_mirInsetBox`), and that size moves with the render
scale. The new `allocs` counter (below) counts these per window.

**Instrument (this PR).** All three backends' `mirrorState()` gain `allocs`, a lifetime count of target
(re-)allocations. `gpu-game-check.mjs` reads the mirror and `memState().churn` at both ends of the armed window, and
`analyseMirrorChurn` (frame-hitch.mjs) turns the deltas into per-frame rates. The Verdict prints them per leg:

```
mirror: drawn <n>/f glass <n>/f renders <n>/f allocs <n> rung <start>><end> churn poolNew=… streamNew=… softReads=…
```

`renders` is printed only when the counter did not restart inside the window.

## 3. The ~89 uniform writeBuffer calls a frame

The sampled `uploads:` rows key a write by its buffer's label, and three labels each uniform buffer with its own id
(`bindingBuffer39_object_(vertex,fragment,compute)`). So one uniform group scatters over hundreds of keys, and the
top-60 cut keeps only a fraction. On the baseline, the rows that survive the cut account for 19.4 of the 88.5
writeBuffer calls a frame (`gpu.writeBuffer` 44 269 over 500 frames):

| group (label with the id removed) | bytes per write | calls per frame in the top 60 | from |
|---|---|---|---|
| `object` | 112 | 16.6 (1.89 KB) | `JB.updateBinding < AP.updateBinding < Rb._update` under `_renderTimed` |
| `render` | 140 | 2.8 (0.38 KB) | the same, under `mirrorEnd` |

**Instrument (this PR).** `gpu-game-check.mjs` now counts EVERY armed writeBuffer by its group (the label with
`bindingBuffer<id>_` and the stage suffix removed; unlabeled buffers are `(none)`), unsampled. It exports
`uploadGroups` and the Verdict prints a `ugroups:` row. Counts: see §Census.

**three.js releases (read 2026-10-30).** r187 is the newest release (published today; no r188).
- mrdoob/three.js#30560 (one UBO per object, written every frame) is still OPEN, with no linked PR:
  https://github.com/mrdoob/three.js/issues/30560
- r187's binding items do not reduce the write count:
  - #35120 "Avoid cache key allocations in _update()" cuts JS allocations per call.
  - #34657 "Avoid recreating initial texture bind groups".
  - #34669 "Reuse binding points for uniform groups" is on the WebGL backend.
  - Release list: https://github.com/mrdoob/three.js/releases
- r186's #34283 (https://github.com/mrdoob/three.js/pull/34283) is a correctness fix for shared uniform buffers, not
  batching. #34288 (https://github.com/mrdoob/three.js/pull/34288) changes the bind-group cache key.
- Depth-only render targets did land in r187: `new RenderTarget(w, h, { count: 0 })`,
  https://github.com/mrdoob/three.js/pull/34782. This is #4272 item 7.

**Verdict: no vendored bump for the uniform writes.** Nothing in r187 batches per-object UBOs. A bump would also
re-diff every vendored patch against #35120, #34657, #34669 and #34919, which all touch the binding and update code.
r187 has had no field time. The migration guide (https://github.com/mrdoob/three.js/wiki/Migration-Guide) also lists
a TSL operand-coercion change (#33695) and a PMREM rewrite (#34585), both of which can change pixels.

## 4. The merged chunk index as a sliding window (TLX, `tlx-chunked.js` `mergeVisible`)

**Before.** GPU hunt 2's range rule kept the leading chunks that did not change and uploaded everything from the first
change to the end. The cull lists a record's chunks in record order (along the arc), so when the HEAD chunk left the
set, every later chunk moved down one slot and the whole set was re-sent. The baseline's largest upload rows are
exactly these: index writes of 200–920 KB from `_renderTimed` and `mirrorEnd`.

**Now.** Each merge slot (main 0, mirror 1, shadow cast 2) remembers which chunks its buffer holds and at what
offset (`s.res` from `s.rb`), including chunks it no longer draws.
- One merge walk in record order finds the longest run of chunks that the new set shares with the buffer. That run
  stays where it is.
- Only the chunks before and after it are written: at most two `addUpdateRange` entries.
- `drawRange.start` moves to the new set's start, so the GPU draws the same indices in the same order. No degenerate
  or extra triangles are drawn.
- A chunk that left the set but is still in the buffer costs 0 bytes when it comes back.
- When the set no longer fits around its run, it is rewritten at the opposite end of the slack, so a steady drive
  uses all of the slack before the next rewrite. With no shared run, it is centred. Starts are even, so a Uint16 range
  is 4-byte aligned.
- The 1.5× headroom now applies at creation as well as on growth; it is the window's slack.

The design choice: per-run ranges with the old fixed layout save nothing, because a head shift moves every offset. A
fixed offset per chunk would draw the culled chunks between visible ones as degenerates on every frame.

**Kept from earlier work:**
- the narrow-index mark (`__apexUint16Index`, PATCHES §20)
- growth and release through `ctx.releaseAttribute` (TLX-WEBGPU-PERF W1/W2)
- the owed-range rule. A range still queued never reached the GPU, so it stays queued. More than 4 owed ranges
  collapse into one span.

A new attribute queues no range. three's create uploads the whole array, and a range queued at creation would be
re-sent on the next update.

**Vendor behaviour this relies on** (three r186 when this was measured; re-read in r187, `vendor/three-0.187.0/three.webgpu.min.js`, after the base moved to it: still one `writeBuffer` per range, and narrow indices take r187's own `BYTES_PER_ELEMENT < 4` write path):
- WebGPU, on Apex's Uint16 path: one `queue.writeBuffer` per range, in list order, with no merge. Each range is widened
  to whole index pairs. The list is cleared after upload.
- WebGL: one `bufferSubData` per range.
- `drawRange.start` is the indexed draw's `firstIndex`.

**Counts (unit tests, real vendor attribute code):**

| step (40 chunks × 600 tris, 20 visible, Uint16) | bytes before | bytes after |
|---|---|---|
| head chunk leaves, a tail chunk enters | 72 000 | 3 600 |
| the head chunk comes back while still in the buffer | 72 000 (full rewrite) | 0 |
| a new head chunk enters | 72 000 | 3 600 |
| a 16-step one-chunk drive, total | ~1 152 000 (16 × 72 000 by the old rule) | 118 800 (one rewrite included) |

Through the vendored WebGPU attribute utility (`tlx-webgpu-perf.test.mjs` W1, 100-triangle chunks), the slide writes
600 / 0 / 600 B per step. The old rule computes to ~12 000 B per step (computed, not run).

Tests:
- `tlx-chunked-lifecycle.test.mjs`: "mergeVisible: the set sliding along the arc by one chunk uploads that chunk, not
  the set after it". It mirrors three's upload into a GPU copy and decodes every step to exactly that set's chunks. It
  fails on the old code: expected 3 600 bytes, got 72 000.
- `tlx-webgpu-perf.test.mjs`: "a one-chunk slide … writes that chunk's bytes".

Cost: the index buffer is 1.5× the set from creation, plus the vendor's CPU shadow copy.

## 5. Exact-zero shader gates (TSL, GLSL, WGSL)

All three gates from GPU hunt 1 shipped on every backend. Each skips only work whose result is multiplied by an exact
0 or is never read:

| gate | condition | why it is exact |
|---|---|---|
| S1: cloud-shadow FBM | `shadow > 0` after `sampleShadow()` | `sampleShadow()` ≥ 0, and `1 − cloud·dim` ≥ 0 (cloud ≤ 1, dim ≤ 1), so 0 × it is +0. Pays only on dry days: overcast presets keep shadowStr < 1, so sunSh never reaches 0 there. |
| S2: car-shadow taps | `carShadowOn > 0.5 && sh > 0` | `sh` is a mean of compare results (≥ 0), and min(0, csh ∈ [0,1]) = 0 |
| TLX-P5-3: lens-dirt fetch | `lensDirt > 0.001 && (bloomAmt > 0.001 \|\| flare on and the sun on-screen)` | `dirt` feeds only `bloomSample` (vec3 0 with bloom off, same 0.001 threshold on all three) and the flare branch, whose own condition is a subset of this one. All uniforms, so the fetch stays in uniform control flow. |

- WGX keeps `textureSampleCompareLevel` inside the new branch (no implicit derivative).
- The TLX and GLX car taps were already inside non-uniform branches.

Gates:
- `wgx-validate.mjs --static` ok, and the bare Dawn run ok with gpuErrors 0.
- `tlx-hunt3.test.mjs` has four new compile tests: GLX and WGX, TLX WGSL, TLX GLSL, and the TLX composite. They
  compile the real materials and check that every gated site sits inside its exact-zero branch. All four fail on the
  old shaders.
- GLX booted and raced on SwiftShader (montreal): backend webgl2, post on, no shader or link error in the console,

## Census #1: the instrumented baseline (41097695730, head 5eb2d97b, instruments only)

macos-latest, montreal, helmet camera, api entry. gpuErrors 0 on all four legs. TLX WebGPU drew 22 passes a frame
(median) over 439 frames.

**Mirror, per frame over the armed window (`mirror:` row):**

| leg | drawn | glass | target re-allocations in the window | rung (start > end) |
|---|---|---|---|---|
| TLX WebGPU | 1.00 | 1.00 | 4 | full > full |
| TLX WebGL2 | 1.00 | 1.00 | 5 | full > lite |
| WGX | 1.00 | 1.00 | 5 | full > lite |
| GLX | 1.004 | 1.004 | 4 | full > lite |

- Item 1 is confirmed by deltas, not by end-of-window reads: one mirror scene pass a frame on every backend.
- The re-allocations are new information. Every backend re-allocates the mirror target 4–5 times in a ~20 s window.
  On TLX the rung did not move, so by code read the cause is the mip need (not isolated by a run):
  `_mirLevels` sizes the chain for the HUD inset in present pixels (`W`/`H`). The governor's render scale moved 1 → 0.9 → 0.5 → 1 in the beats. A smaller buffer
  needs a higher inset LOD, and a grow re-allocates (grow-only, `mirRT.dispose()`). On the other legs a rung change
  (full → lite, res 1.0 → 0.6) resizes the target as well.
- Cost: 4 re-allocations / 439 frames = 0.009 a frame. Each is a texture create (colour, depth and the MRT tag)
  plus fresh bind groups, on a frame the governor has already moved. Sizing the chain for the governor's scale
  floor would remove the regrowth but hold one more level, and on TLX one more level is one more mip render pass on
  every mirror frame. That trades +1 pass a frame for −0.009 re-allocations a frame, so it is NOT taken.

**Uniform writes by group (`ugroups:` row, every call counted), TLX WebGPU:**

| group | writes / frame | KB / frame | bytes per write |
|---|---|---|---|
| `render` | 43.3 | 1.59 | 140 |
| `object` | 35.5 | 2.04 | 112 (model / normal matrices) |
| unlabeled (attributes, indices, instance runs) | 9.4 | 72.4 | — |

That is 88.2 writeBuffer calls a frame (38 741 over 439). 78.8 of them are three's two uniform groups, at 3.6 KB a
frame combined. Both groups are written by three's `Bindings._update` (the sampled stacks: `JB.updateBinding < AP.updateBinding <
Rb._update`); no Apex code writes them, so there is no app-side lever short of a vendored patch. What each 140-byte
`render` block holds was not read out of the minified build here. #30560 is the upstream issue; no release batches it
(§3).

**Churn (`memState().churn`, TLX WebGPU), per frame:** `poolNew` 0.096, `poolPruned` 0.073, `streamNew` 0.005,
`softReads` 0. createBuffer is 0.815 a frame, createBindGroup 0.296, createTexture 0.109. The pool's mints
(`poolNew`, one RenderObject each) explain about 0.1 of the 0.8 createBuffer a frame. The sampled `uploads` rows
attribute 0.2 more (vertex and index `createAttribute`), and the rest fall off the KB-ranked top 60 as small
buffers. Census #2 counts createBuffer by group, unsampled (011d6f38).

## Decisions for Bryce

- **Mirror cadence on a phone's `lite` rung.** Today the mirror renders one scene pass on every frame on `full` and
  `lite`. Drawing 1 in 2 on `lite` would remove a whole mirror scene pass (and its mip build) on every other frame of
  Bryce's default. The cost is visible mirror lag, which the code's own comment calls out ("a mirror that updates at
  half rate reads as lag"). This is a look change, so it is not made here; it needs a device A/B on #3954.
