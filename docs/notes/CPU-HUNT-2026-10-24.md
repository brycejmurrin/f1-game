## The finding that reorders the lane: most of V8's "garbage" is not garbage on the iPhone

Bryce plays on iPhone Safari, which runs JavaScriptCore. JSC NaN-boxes every JS value, so a double is an immediate
and never a heap cell ([wingolog, value representation](https://wingolog.org/archives/2011/05/18/value-representation-in-javascript-implementations);
the tag layout is in WebKit's `JSCJSValue.h`). V8 boxes a double as a `HeapNumber` whenever it escapes a register
into a tagged slot ([v8.dev, mutable heap numbers](https://v8.dev/blog/mutable-heap-number)). The sampling heap
profiles below split cleanly by sampled object size:

| run (monza, 22 cars, player at 55 m/s, throttle) | HeapNumber-class (≤ 16 B) | real objects |
|---|---|---|
| Chromium, `__apex.step` ×1200 after 240 warm steps | 52.7 KB/step | 4.5 KB/step |
| Chromium, the same after 7200 warm steps (2 sim-minutes) | ~52 KB/step | ~4 KB/step |
| game-vm `pumpFrame` ×900 after 4800 warm frames (sim + HUD + camera + audio off; renderer stubbed) | ~82 KB/frame | ~15 KB/frame |

So the ~180 KB/frame that `PERF-CPU-LOAD-2026-10-19.md` measured is ~90 % boxed doubles. They cost Android Chrome
and desktop, and nothing on Bryce's phone. Rank allocation work by the **real-object** column for the iPhone, and by
CPU ms for everyone. Method: `HeapProfiler.startSampling({samplingInterval: 512, includeObjectsCollectedByMajorGC,
includeObjectsCollectedByMinorGC})`, then invert each sample's scaled size `S = s / (1 - e^(-s/512))` to recover
the object size `s`.

V8 tiering on the same run (`--trace-opt --trace-deopt`): `updateCarLateral` stays in **Maglev** for the whole first
1440 steps (~24 s of racing), deopting on "insufficient type feedback" each time a new branch runs. The others reach
TurboFan by ~step 1000. The warm-up window is where the extra ~45 KB/step of boxing sits (98 → 58 KB/step after 2 min).
That is a V8 JIT property, not a fixable allocation site, and it does not apply to JSC.

## Measurements

- Physics step, Chromium desktop, steady state: **0.61 ms/step** (1200 steps, CPU profile at 100 µs). Self-time top:
  `updateCarBrakePlan` 3.1 %, `AudioParam.setTargetAtTime` 3.0 %, `updateCar` 3.0 %, `updateCarLateral` 2.2 %,
  `update` 1.8 %, `spline.sample` 1.5 %; 49 % `(program)`.
- Real rAF frames (`tools/perf/profile.mjs monza --mode spans --frames 90`, SwiftShader, so the render rows are not
  device evidence): physics p50 5.3 ms for ~4.9 catch-up steps per frame (~1.1 ms/step), ai p50 0.7 ms per step,
  **hud p50 0.6 ms, p95 10.8 ms, p99 43 ms**, camera p50 < 0.1 ms, audio p50 < 0.1 ms per step.
- Native calls per physics step (wrapped prototypes, monza, sound on): `setTargetAtTime` ~9.5 (aimParam 3.25,
  aimGain 2.88, setEngine ~2.1), `MediaQueryList.matches` 1.0 (`Input.touchControlsNeeded` via `autoThrottle()`).
- HUD tick at 844×390 touch, ~110 frames: `updateHud` ~1.4 ms per tick inclusive. Of that: `fitHud` 0.45 ms,
  `phoneFitStampSync` 0.23 ms, `announceLaneTick` 0.22 ms. The self time is native: `getBoundingClientRect`
  29 ms total (`laneRect` 17.6 ms, forced layout), `querySelectorAll` 17 ms (`HudLayout.clearReadouts`, mostly from
  the ResizeObserver callback at `hud-layout.js:895`), `getPropertyValue` 12.7 ms (`hud-relative.js fitRows`).
