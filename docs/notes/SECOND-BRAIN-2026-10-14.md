# Second brain — Obsidian and agent memory, weighed (2026-10-14)

Research behind the knowledge guards in `tests/unit/agent-config.test.mjs` (hidden-Unicode, memory `source:`) and `tests/unit/docs-integrity.test.mjs` (`Supersedes:` pairs). Three parallel web passes (Obsidian for agents, memory tools, knowledge practice) plus `AGENT-MEMORY.md`; the backlog half is `AGENT-WORK-TRACKING-2026-10-14.md` (PR #1519). Sources inline; nothing below was measured on this box except the repo facts named.

**Shipped from Step 1 (2026-10-14):** the hidden-character test, the `source:` check, the two-way `Supersedes:` / `Superseded by:` check, `.obsidian/` gitignored, and a monthly knowledge-audit Routine.

Adopt Obsidian only as a free, read-mostly **viewer** of the repo's existing `docs/` tree on desktop and phone. Do not adopt Obsidian, or any other "second brain" or agent-memory service, as a new store the agents read and write. The fleet's knowledge layer already matches the design that Anthropic, OpenAI, Cursor and GitHub converged on in 2025–26: a small always-loaded map (AGENTS.md), detail loaded on demand (path-scoped rules, skills, `docs/`), and a small reviewed memory of preferences and corrections. It also has the property no hosted tool gives you: every write is a git diff that CI checks and a human can review. Every candidate fails at least one hard constraint. Obsidian's query features need the desktop app running. Notion is OAuth-only. Mem0, Zep and Letta add a secret to every container and write "facts" silently. Graphiti and Cognee need a server and an LLM key. Logseq needs the desktop app. The MCP reference server keeps one JSONL file that merges badly. The two real risks you face are context rot from stale near-duplicate notes and poisoning of agent-written memory, and both are made worse by adding a second store. The money is better spent on three small upgrades to what you already run: citation-checked memory entries, a hidden-Unicode lint on agent-facing files, and an explicit supersede convention for dated notes. Basic Memory, used in-repo over a folder, is the only tool worth a later trial, and only if grep over `docs/` stops being enough.

## Memory, docs and tracking are three jobs, and you already fill all three

The prior research settled work tracking: GitHub Issues hold not-yet-started work, the draft-PR body is the in-flight log, and `who-is-on-it.mjs` is the cross-container lock. That decision shapes this one. A second brain is not a backlog, and anything that holds task status ("doing X", "blocked on Y") belongs in an issue or PR body. In a memory store it goes stale within hours. What remains is durable knowledge: rules, measured lessons, preferences, conventions and decisions.

The vendors now describe the same design for that. Anthropic's context-engineering guidance is to find "the smallest set of high-signal tokens", keep "lightweight identifiers" (paths, links) up front and load content just-in-time with tools. Its example is Claude Code itself: CLAUDE.md loads up front and grep/glob fetch everything else ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Claude Code's docs give the same split in practice. Instructions live in CLAUDE.md, with a **target of under 200 lines** because "longer files … reduce adherence". Procedures and path-specific rules move to skills and `.claude/rules/`. Auto memory is a `MEMORY.md` index of which **only the first 200 lines or 25 KB load**, and it skips anything derivable from the code ([Claude Code memory docs](https://code.claude.com/docs/en/memory)). Cursor says to keep rules under 500 lines, reference files instead of copying them, and add a rule only after a repeated mistake ([Cursor Rules](https://cursor.com/docs/context/rules)). OpenAI's Codex harness post reportedly calls AGENTS.md "a map, not a 1,000-page instruction manual", with `docs/` as the system of record; that comes from a secondary write-up, because the primary post returned 403 ([tutorialsdojo summary](https://tutorialsdojo.com/?p=40053)).

This repo maps onto that one to one, as the table shows. Karpathy's widely copied "LLM wiki" pattern is raw sources, an LLM-maintained interlinked markdown wiki, a schema file, plus ingest, query and lint operations, usually viewed in Obsidian ([Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)). It is the same structure: code and CI logs are the raw sources, `docs/` and dated `docs/notes/` are the wiki, AGENTS.md is the schema, and the docs-integrity test is the lint. A separate vault would be a second copy of that wiki that drifts from the code it describes.

| Job | Store in this repo | Written by | Loaded |
|---|---|---|---|
| Instructions (the map) | `AGENTS.md` via `CLAUDE.md`, `.claude/rules/` | human, reviewed; length test-capped | every session; rules by path |
| Procedures | `.claude/skills/` | human or agent via PR | on match |
| Reference and evidence | `docs/`, dated `docs/notes/*`, indexed in `docs/README.md` | agents via PR, docs-integrity tested | just-in-time by grep or Read |
| Preferences and corrections | `.claude/memory/` (auto memory, three-way synced) | Claude, committed with the work | index every session |
| Backlog / in-flight / lock | Issues / PR body / claims board | agents | by query |

The evidence on what such files are worth argues for the small-map approach rather than against it. An ETH study found context files "do not generally improve task success rates" and raise inference cost by more than 20%. It found **repository overviews unhelpful** and non-standard practices useful ([arXiv 2602.11988](https://arxiv.org/abs/2602.11988)). A second study measured **28.64% lower median runtime and 16.58% fewer output tokens** with AGENTS.md across 124 PRs ([arXiv 2601.20404](https://arxiv.org/abs/2601.20404v1)). Read together, they say terse, non-obvious, operational content pays and tours of the architecture do not. Both studies point toward less always-on prose, not a larger vault.

## Obsidian helps you read docs, not your agents

Obsidian splits into two products for this question.

As an **agent-facing store** it adds nothing a container can use. There is no official Obsidian MCP server. The official CLI (1.12) "requires the Obsidian app to be running" ([Obsidian CLI docs](https://raw.githubusercontent.com/obsidianmd/obsidian-help/master/en/Extending%20Obsidian/Obsidian%20CLI.md)). The official headless client `ob` is, in CEO kepano's words, "for now … just a Sync client" ([HN](https://news.ycombinator.com/item?id=47197267)). It is closed source ("UNLICENSED"), at version 0.0.14, and logs in with email, password and MFA flags, with no documented token ([npm](https://registry.npmjs.org/obsidian-headless)). The most popular MCP route, the Local REST API plugin, serves on `127.0.0.1:27124` from inside the desktop app ([README](https://raw.githubusercontent.com/coddingtonbear/obsidian-local-rest-api/master/README.md)). A cloud container could reach it only through a tunnel to a Mac that is always on. The headless filesystem servers are MCPVault, which says "Obsidian does not need to be running" ([README](https://raw.githubusercontent.com/bitbonsai/mcpvault/main/README.md)), and StevenStavrakis `obsidian-mcp` v2, which does offer revision preconditions for concurrent edits ([README](https://raw.githubusercontent.com/StevenStavrakis/obsidian-mcp/main/README.md)). Over a checked-out folder, both reduce to what Read, Edit and `rg` already do, and they add tool schemas that cost context: one guide measured **58 tools across five servers at about 55k tokens** ([parallel.ai](https://parallel.ai/articles/best-mcp-servers-for-claude-code)). The features that make Obsidian distinctive are backlinks, Bases queries, Dataview and the graph. They are computed only inside the app, so headless agents never see them. Practitioners running Claude Code on a vault mostly drop MCP and use ripgrep plus a rules file ([okhlopkov](https://okhlopkov.com/second-brain-obsidian-claude-code/)).

As a **human viewer** it is worth the five minutes. The app is free, including for work, since February 2025 ([pricing](https://obsidian.md/pricing)). It opens any markdown folder. Pointed at a desktop clone of `docs/`, it gives you a graph of the 105 dated notes, backlinks ("what cites this note?"), fast full-text search, and Bases dashboards over any frontmatter the agents keep. That is the human half of Karpathy's pattern, and it costs the agents nothing.

The phone is the weak link. The obsidian-git plugin's own README warns mobile users that it "is highly unstable" and recommends against it ([obsidian-git](https://raw.githubusercontent.com/Vinzent03/obsidian-git/master/README.md)). The practical routes are a separate git app (Working Copy on iOS, GitSync) that pulls the repo into the vault folder, or Obsidian Sync at **$4/month annual** ([pricing](https://obsidian.md/pricing)). Sync merges markdown conflicts with diff-match-patch, which the help pages admit "may sometimes create duplicate text" ([Sync troubleshooting](https://raw.githubusercontent.com/obsidianmd/obsidian-help/master/en/Obsidian%20Sync/Troubleshoot%20Obsidian%20Sync.md)). Sync would also create a second history outside git. Since you already read PRs and issues in GitHub Mobile, rendered markdown on github.com covers most phone reading for free. Obsidian on the phone is a comfort upgrade, not a capability.

One compatibility fact decides how to set it up. `docs/` currently contains **zero `[[wikilinks]]`**; it uses relative markdown links, which the docs-integrity test resolves and GitHub renders. Wikilinks do not render on GitHub. If you open `docs/` in Obsidian, set "Use [[Wikilinks]]" off so that any note you write on the phone keeps the format the test and GitHub understand.

## Every dedicated memory service fails a hard constraint

The memory-tool field sorts by storage model, and the storage model decides how each tool fares against your constraints.

| Option | Cost | Headless from ephemeral container | Phone | Concurrent writes | Reviewable / poisoning | Verdict |
|---|---|---|---|---|---|---|
| Current stack (git markdown + synced auto memory) | $0 | Yes; already wired | GitHub Mobile | Three-way merge, PR review | Every write is a diff; secret-scanned | **Keep** |
| Obsidian as viewer over `docs/` | $0 (Sync $4/mo optional) | n/a (human only) | Good with Sync; fragile via git | Human writes only | Same as git | **Adopt for reading** |
| Basic Memory, local, in-repo folder | $0, AGPL-3.0 | Yes (reindex at start) | Via git | Git merge | Markdown diffs | **Trial later, only if grep fails** |
| Basic Memory Cloud | $15/seat/mo | API key (MCP auth unverified) | Web editor | Server-ordered; rclone sync | Writes outside PR review | Avoid now |
| MCP reference memory server | $0, MIT | Only if JSONL committed | None | File lock; one-file merges | Opaque JSON | Avoid |
| Mem0 / Zep / Letta hosted | Free tiers; $19–$375/mo | API key secret per container | Little to browse | Server-side | LLM-extracted facts, silent writes | Avoid |
| Graphiti / Cognee self-hosted | Infra + LLM per write | Needs a running server | None | Queued | Opaque graph | Avoid |
| Obsidian MCP (REST/CLI/plugin) | $0 | No: desktop app required | n/a | n/a | n/a | Avoid |
| Logseq / Tana Outliner | $0 | No: desktop app API | Good | n/a | n/a | Avoid |
| Notion | Free | No: hosted MCP is OAuth-only | Excellent | Server | Proprietary blocks | Avoid for agents |

The details behind the verdicts follow.

**Basic Memory** is the best of the dedicated tools. It stores markdown with frontmatter, typed relations as wiki-links and a local SQLite index with hybrid full-text plus vector search, and it imports the MCP reference server's format ([README](https://github.com/basicmachines-co/basic-memory)). Run locally over a folder in the repo, it keeps git as the source of truth, which is why it gets a conditional trial. Its Cloud tier costs **$15/seat/month** and syncs through rclone with git as only a manual option ([README](https://github.com/basicmachines-co/basic-memory)). That would move agent writes out of PR review.

**The MCP reference server** keeps a single JSONL file behind a lock file that is unsafe on network filesystems ([modelcontextprotocol/servers](https://github.com/modelcontextprotocol/servers/tree/main/src/memory)). Committed to git, concurrent sessions would conflict on that one file.

**The hosted extractors** are cheap to start. Mem0 Hobby is free for 10k adds a month and Starter is $19 ([Mem0 pricing](https://mem0.ai/pricing)). Zep Free is 10,000 credits and Flex $125 ([Zep pricing](https://www.getzep.com/pricing)). Their benchmark claims are vendor-run (Mem0 reports 92.5% on LoCoMo; [Mem0](https://mem0.ai/blog/ai-memory-benchmarks-in-2026)), and an independent audit found **6.4% of LoCoMo's answer key wrong** and an LLM judge that accepts up to 63% of deliberately wrong answers ([Penfield Labs](https://penfieldlabs.substack.com/p/we-audited-locomo-64-of-the-answer)). No source in this research shows a coding agent doing better with an MCP memory server than without one.

**Graphiti** is the one tool with real temporal validity: it invalidates old facts instead of overwriting them. Thoughtworks rates it "Trial" but warns of per-write LLM cost and pre-1.0 status ([Thoughtworks Radar](https://www.thoughtworks.com/radar/platforms/graphiti)). Its MCP server calls itself "experimental" and needs FalkorDB or Neo4j plus an LLM key ([graphiti/mcp_server](https://github.com/getzep/graphiti/tree/main/mcp_server)). Temporal graphs pay off when facts change constantly, such as customer state. A coding fleet's memory is low-volume and high-precision: preferences, gotchas, conventions.

**The desktop-bound and OAuth-bound tools** drop out on access alone. Notion's hosted MCP needs interactive OAuth, and its token server is unmaintained ([Notion](https://developers.notion.com/docs/get-started-with-mcp)). Logseq's community MCP servers drive the desktop app's local HTTP API ([contextbolt](https://contextbolt.com/blog/logseq-mcp/)).

**Claude's built-in memory** is the option you already run. Auto memory is "machine-local … not shared across machines or cloud environments" ([docs](https://code.claude.com/docs/en/memory)), which is exactly why `memory-sync.sh` exists. The repo measured that the first naive sync "reverted other sessions' memories (twice in one day)". It replaced it with a three-way merge against a baseline, a line-merged index and a `CONFLICT` print, all driven by `tests/unit/memory-sync.test.mjs` (`docs/notes/AGENT-MEMORY.md`). That hard-won concurrency handling is something no hosted vendor documents for same-note races. The API memory tool (`memory_20250818`) lets an application back `/memories` with any store ([platform docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)). It matters only if you build your own harness.

## Staleness and poisoning, not storage, are the real risks

Chroma's context-rot study ran 194,480 calls across 18 models. Accuracy **fell with input length in every experiment**. A single topically similar distractor cut accuracy, and four cut it further. On LongMemEval, focused prompts of about 300 tokens beat full ones of about 113k tokens on every model ([Chroma](https://www.trychroma.com/research/context-rot)). A superseded note that sits beside its replacement is exactly that distractor. Claude Code's docs add that when two instructions conflict, Claude "may pick one arbitrarily" ([docs](https://code.claude.com/docs/en/memory)). A second brain that accumulates dated notes, synced chat summaries and agent "observations" in a parallel vault therefore lowers accuracy by default. Pruning and superseding matter more than capture.

The most concrete anti-staleness mechanism any vendor ships is GitHub Copilot Memory. Each repository fact **carries citations to code**, is re-checked against the current branch before use, and **is deleted after 28 days unused** ([GitHub Docs](https://docs.github.com/en/copilot/concepts/agents/copilot-memory)). Claude Code's `/doctor prompt-audit` (v2.1.283+) is the complementary audit: it reports outdated instructions, dead references and cross-file contradictions across CLAUDE.md, AGENTS.md, rules and skills ([docs](https://code.claude.com/docs/en/memory)). Both can be reproduced here with a test rather than a service.

Poisoning is now an established attack class. Pillar Security's "Rules File Backdoor" hid instructions in invisible Unicode inside Cursor and Copilot rules files ([The Hacker News](https://thehackernews.com/2025/03/new-rules-file-backdoor-attack-lets.html?m=0)). A July 2026 paper shows memory-file payloads attacking current and future sessions and recommends guarding memory *updates* ([arXiv 2607.14611](https://arxiv.org/abs/2607.14611)). The CSA reports **71.4% success** for one-email false-memory injection against a Claude Code SDK agent (secondary figure, primary not read; [CSA Labs](https://labs.cloudsecurityalliance.org/research/csa-research-note-memghost-ai-agent-memory-injection-2026072/)). An ICML 2026 study found existing prompt-injection defenses do not cover memory poisoning ([ICML](https://icml.cc/virtual/2026/67964)).

Two properties of your setup matter here. Memory changes ride PR diffs, and `agent-config.test.mjs` already caps the index at 200 lines, requires typed frontmatter and rejects secret-shaped strings. The gap: **no test scans agent-facing files for zero-width or bidi characters**, which is the exact Rules File Backdoor vector. The only hidden-Unicode handling found in `tests/unit/` is in game features (lobby codes, settings export). A hosted extractor would remove the review checkpoint entirely, because it writes silently from whatever the agent read, including PR comments and web pages.

## Concrete setup: three guards, one viewer, one tripwire

**Step 1: harden what exists.** These go in one PR, a tools/tests change verified with `npm run test:tooling-fast`.

1. *Hidden-Unicode guard.* Extend `tests/unit/agent-config.test.mjs` to reject U+200B–U+200F, U+202A–U+202E, U+2060–U+2064 and U+FEFF in `AGENTS.md`, `CLAUDE.md`, `.claude/rules/`, `.claude/skills/`, `.claude/agents/`, `.claude/memory/` and `.claude/agent-memory/`.
2. *Copilot-style citations for memory.* Add an optional `source:` field to each memory topic file's frontmatter: a repo path, test name, PR number or the literal `user`. The test fails when a cited path no longer exists. That turns "an entry that contradicts the code is stale" from advice into a check.
3. *Supersede convention for dated notes.* When a `docs/notes/` ledger is replaced, the new note's first line names the old one (as `AGENT-MEMORY.md` already does), and the old entry's line in `docs/README.md` is marked superseded or removed, so agents grepping `docs/` do not meet two live answers.
4. *Periodic audit.* Run `/doctor prompt-audit` (or the existing `total-audit` skill) monthly as a scheduled Routine. Leave work-status out of memory: anything shaped like "in progress" belongs in an issue.

**Step 2: add Obsidian as a reader.**

- *Desktop.* Open the repo root as a vault, or only `docs/` to keep the graph clean. Gitignore `.obsidian/` and `.smart-env/`, turn wikilinks off, and set new notes to land in a git-ignored `scratch/inbox/`.
- *Phone.* Try it free first: Working Copy or GitSync cloning the repo read-only into an Obsidian vault folder, refreshed on demand. If that grates, pay $4/month for Sync on a personal vault that holds only your inbox, and keep it out of the repo.
- *Capture.* Capture an idea as a GitHub issue (the backlog) or as an inbox note that an agent later files into `docs/notes/` or `.claude/memory/` through a PR. Never let a container run `ob sync` or reach your vault.

**Step 3: decide later, by measurement.**

- *Trigger for Basic Memory.* Trial Basic Memory locally over `docs/` only if agents demonstrably miss relevant notes that grep should have found, for example a repeated lesson that a CI-red triage could have found in `docs/notes/`. Add it as a stdio MCP with the SQLite index rebuilt at SessionStart, read-only for agents, and keep git as the only writer.
- *Never.* Do not install an app-bound Obsidian MCP, a hosted extractor (Mem0, Zep, Letta, Supermemory), a graph server (Graphiti, Cognee) or Notion as agent memory. Do not use Obsidian Sync or iCloud as a second source of truth for anything an agent reads.

## Conclusion

The research inverts the usual second-brain pitch. For a solo developer with an agent fleet, the scarce resource is not storage or recall but the attention budget of each session and the trustworthiness of what fills it. Every write path you add is another place for stale or hostile text to persist. The repo's real asset is that all knowledge passes through one reviewed, tested channel, and its own measured incident shows that a second channel (the naive memory sync) erased other sessions' work within a day. The upgrades that matter are therefore mechanical checks on that channel: citations that must resolve, hidden characters that must not appear, and superseded notes that must say so. A new home for knowledge would not help.

Uncertainties remain. The evidence on whether any memory layer improves coding-agent outcomes is thin and conflicting. No independent SWE-bench-style study of MCP memory servers turned up. Phone-side git reliability for Obsidian in 2026 was not measured. If those numbers arrive and favour a tool, Basic Memory over the in-repo folder is the one candidate that can be added without giving up git as the single source of truth.
