# Perf P1 — track build, mesh build, shared/GLX render (2026-10-18)

Worker P1 of the 2026-10-18 perf fleet (owned paths: `js/track/**` engine,
`js/render/shared/**`, `js/render/glx/**`, `tools/track/**`, `tools/perf/**`).
This note records every finding, fixed or not, with its measurement. The
measuring tools are scratch scripts (`scratch/p1/`, not committed). Each
section says which tool produced which number.

## How it was measured

- **Plain-realm build timer.** The `TRACK_VM` manifest is loaded with
  `vm.runInThisContext`, so the files share one realm's script scope and no
  contextified global sits in the way. `Tracks.build` is timed per circuit:
  one warm-up, then the median of 2–3 builds, with a forced GC between builds.
  PERF-FINDINGS showed that the verify-track VM inflates functions that read
  bare globals. This session hit that again (see §3), so hot spots are ranked
  from the plain realm only.
- **Browser timer.** Playwright on the container's SwiftShader, 844×390,
  `apex26.forceMobileTier=1`, GLX (`apex26.gfxBackend=webgl2`). For each
  circuit it calls `__apex.race(id)` and reads `buildProfile()` and
  `raceProfile()`; a CDP CPU profile is taken on the last repeat.

## 1. FIXED — grid-backed hint-less `Tracks.project` (PR: perf/track project grid)

`js/track/core/spline.js`: a lazily built segment grid (`track._segGrid`,
32 m cells, CSR typed arrays, keyed on the `px`/`pz` arrays it was built
from). The search walks rings of cells outward from the query, each clipped to
the grid. It stops once a ring cannot hold a segment as close as the best cost
so far: `cost >= XZ distance²` whether or not the height term is used. Ties go
to the lowest segment index, which is what the ascending scan's strict `<`
picked. The hinted (windowed) path is untouched.

- **Equivalence.** `JSON.stringify` of the old and new results compared on
  every circuit in `Tracks.LIST`: 52 circuits, 277,405 probes (4,000 random
  points per circuit, then 1,500 after the far-query fix; every node, every
  segment midpoint, 12 m offsets, far and non-finite queries, and hinted
  queries). **0 mismatches.** Pinned by `tests/unit/spline-project-grid.test.mjs`
  (deepEqual against a verbatim copy of the old scan).
- **Speed, plain realm.** 20,000 probes within 100 m of the centreline, no
  hint, half carrying a height (µs per call, before → after): monza
  18.2 → 2.3, spa 44.6 → 3.3, monaco 13.1 → 2.4, silverstone 19.7 → 2.4.
- **A trap found while writing the test.** The first cut walked every cell of
  every ring from r = 0. A query 3,000 km off the circuit spent minutes walking
  empty rings. The rings are now clipped to the grid, and the walk starts at
  the first ring that touches it.

## 2. Not taken — build-phase micro-wins (flat profile)

Plain-realm self time over 21 builds of seven circuits (17.1 s total): GC 10 %,
terrain `ribbon` 6.5 %, `_triY` (terrainY) 5.3 %, `onTrack` 5.2 %, accumulator
`push` 5.1 %, `compact` 4.0 %, `grid.query` 3.6 %. No single row is worth a PR
on its own. Two were already tried and rejected in comments in the code:

- `nodeGrid` CELL split for the terrain clip: 0–7 % of buildTerrain, under 1 %
  of a build (`js/track/core/mesh.js` comment).
- The `emit()` scalar rewrite: bit-identical, but 0–4 % and negative on vegas
  (PERF-FINDINGS).

## 3. Not taken — Spa pine `clash` scan (a VM artefact)

In the verify-track VM, `nature.js` pine `clash` was the top self row:
2.46 s of 17.2 s across three circuits, and 4,572 clash calls on Spa. A
typed-array plus precomputed-parallel-pairs rewrite left the VM time unchanged
(spa VM ~2.2 s). In the plain realm the row is gone: `pine` self is 205 ms over
21 builds. The cost was the VM's slow `Math` global lookups in the hot loop,
not the algorithm. Reverted. This is another instance of PERF-FINDINGS' "rank
from a plain realm".

## 4. Open leads (measured, not fixed this round)

- **`ChunkBins.bin`** (`js/render/shared/chunk-bins.js`) grows a JS array for
  each bucket. It takes 26–51 ms (median) on node desktop for the props of
  monza, monaco and vegas, on the main thread inside the GLX and TLX upload.
  A two-pass typed-array bin would keep the same buckets.
  `tests/unit/lamp-chunks.test.mjs` deepEquals `bk.idx` against a plain array,
  so the change touches that pin.
- **GLX dust chunks.** Monaco props bin to 1,529 chunks, and 1,324 of them hold
  48 triangles or fewer. Monza has 428 of 640, vegas 626 of 904. TLX folds
  these (its dust merge). GLX's contiguous run-merge collapses only neighbours
  in index order. A GLX fold changes per-chunk lamp sets, because the union
  AABB pulls in more lamps. It needs a night parity check and a gpu-census
  A/B, not a software probe.
