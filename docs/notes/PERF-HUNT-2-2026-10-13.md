# Perf hunt 2, 2026-10-13 — four read-only Opus agents on tip 1753201f6

Bryce asked to "fix all or investigate other performance improvements using opus agents" after the
three.js hunt (`TLX-PERF-HUNT-2026-10-11.md`, PRs #1445–#1447) was fully landed. This round leaves the
three.js shaders alone and takes the rest of the frame: the fixed-step SIMULATION (what `update()` costs
per step), the per-frame JS between the sim and the GPU plus the HUD DOM (FRAME), the hand-written
WebGL2 backend (GLX, the fallback and the look reference) and TIME-TO-RACE: the track build, boot and
memory (BUILD). Each agent read the code, counted from it and, where the Node harnesses allow, measured:
the sim and frame hunters ran the REAL `js/game.js` in `tools/lib/game-vm.cjs` (22 cars, montreal), the
build hunter timed 104 builds (52 circuits × day/night) in a plain Node realm with an md5 over every
buffer. No browser, no GPU. GPU-side figures (GLX) are arithmetic. The parent session seeded the sim
slice with a headless V8 profile (`tools/shot/profile-gameloop.mjs montreal physics`: of the JS inside
the step window, GC is 16 %, `update`+`updateCar` self time 27 %) and reproduced the first finding
before writing this note: with the keyed predeclare 0 of 22 car objects have fast properties; with
named stores 22 of 22 do, the 14-field state digest is identical, and the VM step is 2.69 → 2.41 ms.

The four reports follow verbatim as §A–§D (their `scratch` scripts lived in the session's scratchpad and
are gone with it; the `tree/` mirrors were symlink copies of this tip with one patched file). Confidence
is each hunter's own: CONFIRMED = traced from the real per-frame caller or measured in a harness;
SUSPECTED = reading only, or the mechanism is confirmed but the size is not.

### Profile summary (parent's run landed: `montreal physics`, 45,227 samples)

* 93.2 % of samples are `getError` (GPU sync) — not JS. JS = 1218 ms; the `__apex.step(1/60, 600)`
  window is 1057 ms: **step code 883 ms = 1.47 ms/step, GC 173 ms = 0.29 ms/step (16.4 % of the
  window)**, other 0.6 ms.
* `update` inclusive 870.6 ms: `updateCar` 524 (60 %), update self 158 (18 %), `resolveCollisions`
  71 (8 %), `setEngine` 54 (6 % — per STEP here only because `__apex.step` sets `_audioParamStep`;
  in `tickBody` it is once per frame), `race-radio update` 31 (3.6 %), coach 6.9, fillArcBuckets 4.5.
* `updateCar` inclusive 525 ms: self 157 (30 %), tyre `update` 36.8, `scanTraffic` 30.1 (→ forArcNear
  29), `brakeDecision` 26.8, `engineer.update` 22.1, `pits.think` 17.9, `playerForces.step` 12.6,
  `curvature` 12.4, `WallClamp.apply` 12.3, `inAeroZone` 11.3, `worldFromTrack` 9.3, Input
  `braking`/`throttle`/`steer` 7.6/7.2/6.2, `bankAngle` 7.2.
* Oddity: 349 of update's 430 self ticks sit on **line 4576** — the `for (const c of cars)
  updateCar(c, dt, ranked)` call line (≈128 ms, 0.21 ms/step). Consistent with tier-transition /
  baseline-prologue cost of entering a 264-register function (see S1); not proven.
* Confirms: S1 (GC share, updateCar self, non-inlined helper frames like `curvature`, `wrapS`,
  `vTop`, `gripMult`, `damp` showing as separate frames), S4, S5, S7, S8. Contradicts nothing; it
  does show the AI lookahead (S6) is smaller than the read suggested (~25 ms/600 steps).
* Caveat for the parent: the window is steps 0–600 after `go()`, which is exactly when `updateCar`
  is still unoptimized in the VM timeline (first TurboFan at step ~390) — the profile over-weights
  the baseline tier. A profile of steps 3000–3600 would show the steady state.

- **Buffers:** every dynamic buffer grows by `bufferData` and refills with `bufferSubData` (glow, particles,

**Build loop**
- **Paced build overhead.** 1.02–1.18× of work. Not a lever; the issue is the largest single step (T1 fixes

## Fix pass, 2026-10-13 — lessons so far

7. **A SwiftShader capture is governor-state-dependent unless the governor is pinned.** The frozen
   `backend-compare.mjs` scene is deterministic (two base captures matched at MAD 0.000), but the perf
   governor evaluates the slow software frames in the ~3 s before `freeze(true)` and on some runs sheds
   a tier (lamp spot shadows at tier 2; SSAO / god rays / bloom at tier 4) and on others does not. Vegas
   night came back at mean luma 70.18 or 68.83 (lamp shadows shed or kept) and with or without a ±1
   whole-frame post pattern, on the BASE tree as much as on the lane tree, and the first lane-vs-base
   diff (MAD 1.48, 20k px) was two governor states, not a shader change. The tool now pins the governor
   (`__apex.renderScale(1)` + `PerfGov.setTierHold(true)` right after the race starts, `--gov-free`
   opts out) and records `state.perf` (tier, autoShed, scale) in the manifest, so a manifest proves the
   two sides were comparable.
8. **Before blaming a commit, get the same-tree floor from at least two captures of EACH tree, and
   diff pairs that share a recorded state.** Three base and three lane captures of Vegas night paired
   off at MAD 0.000 once sorted by state; the bisect captures that "reproduced" the darkening had simply
   landed in the other state.
