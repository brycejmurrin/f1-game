# AUDIT tools-ci — tooling, build and CI (pinned e80823076a2413edfe4edfd68ce58b5d793b6904)

## 1. Summary

- What this slice is, as found: about 620 Node/shell/Python scripts under `tools/` (≈140k lines), 23 workflows, 4 git hooks, a set of Claude hooks, three in-repo MCP servers behind an output gateway, and packaging wrappers (Electron `desktop/`, Capacitor `mobile/`, a Cloudflare signalling `worker/`). There is no build: "build" means 15 `--check`-able generators plus a deploy-time stamp (`bump-cache`) that rewrites `?v=` keys and SRI maps into a staged `_site`.
- The merge gate is not a CI job. The ruleset requires one commit status, `gate`, which `land.yml` posts after `tools/ci/merge-gate.mjs` passes seven rows; the `ci` row reads the check-run `CI` (ci.yml's `ci-verdict`). The verdict aggregator itself is sound (19 crafted inputs, none wrongly green). The holes are around it: what the PR tier selects, what the deploy train reuses, and who may edit the gate's own code.
- One player-visible defect was confirmed on the live site: the deploy stamp omits two lazy rosters, so the garage's real-circuit exterior and the `?gfxdebug=1` panel can never load on Pages (TC-01).
- CI truth: on a js-only PR several VM unit suites (including the driving-model characterization) run in no PR job; the Pages train can then reuse that PR run instead of running its own; a run that only passed on a whole-run re-run is accepted as both merge gate and deploy gate (this is how the pinned HEAD shipped).
- Guards: most checkers do go red when fed a bad input (about 60 mutation tests across the slice went red as designed). Around 20 do not: they exit 0 on the defect they exist to catch, or pass vacuously on an empty scope.
- Generated files are reproducible byte for byte and `gen:check` goes red on drift; manifest, index.html and sw.js agree (611 js files, 323 script tags, all in rosters). That part is healthy.
- Agent hooks (`bash-guard`) are both leaky (trivial respellings pass) and over-broad (block browser-free modes the docs recommend), so the "(hook)" rules in AGENTS.md are weaker than stated.
- Dead weight: 86 files / ≈6.3k lines under `tools/` are reachable from nothing (58 of them `tools/environment/`, written for a `/workspace` host that does not exist here), plus 39 MB of unshipped gallery images in `examples/`.
- Scheduled automation is partly broken without anyone being told: `garage-before` red for 14 days, both fold workflows have never opened a PR, flake-tally's base-red detector has blind windows and can close its own issue on API errors.
- Overall: the core (verdict aggregation, generators, stamp check, loopback/token discipline in the MCP HTTP servers, SHA-pinned actions, no `pull_request_target`) is solid. The weak layer is selection, reuse and self-protection of the gate, plus a long tail of tools whose exit code does not reflect their verdict.

Method: 17 Opus reader subagents, one per sub-slice, each reading its files in full and running/mutating tools in a scratch copy; then 17 independent Opus verifiers given only `file:line` + claim (not the finder's reasoning). About 200 claims went to verification: 6 were refuted and dropped, about 25 were narrowed or downgraded (rows below carry the narrowed form). KNOWN = recorded in docs/BUGS.md, DEFECT-LEDGER, a docs/notes survey, an open issue or the file's own header.
